# الخطة الثالثة — الفحص الأمني والإصلاح

## تكليف المساعد المنفذ وحدود التفويض

افحص موقع ياسمين الشام كاملًا لأن المتجر والإدارة والرواتب والخدمات تتشارك البنية، ثم أصلح المشكلات وفق الأولوية مع الحفاظ على البيانات وسلوك العمل. هذه خطة أُعدت في 19 سبتمبر 2026؛ لم تُطبق منها إصلاحات. يبدأ التنفيذ بتكليف لاحق من المالك. لا تختبر استغلالًا هدامًا على الإنتاج ولا تنشئ فاتورة أو دفعة فعلية؛ استخدم نسخة تجريبية ببيانات مصطنعة لإثبات مشاكل التعديل والحذف.

## الأدلة الأولية وماذا تعني

الفحص الحالي: قراءة الكود، lockfile، ملفات الترحيلات، واستعلام metadata مباشرة على مشروع Supabase `qbbijtyrikhybgszzbjz` مع Security Advisors. لا توجد قراءة لمحتوى صفوف العملاء أو صورهم. النتائج التالية ليست تقرير اختبار اختراق مكتملًا.

| المعرف | الأولوية | الدليل | الاستنتاج وحدوده |
|---|---|---|---|
| SEC-01 | عاجلة/حرجة إذا كان المسار منشورًا والمفتاح فعّالًا | `src/app/api/soniox-token/route.ts:3-11` يعيد `SONIOX_API_KEY` في JSON دون تحقق هوية | كشف سر ثابت مثبت في الكود. لم يُستدعَ endpoint الحي ولم يُجلب المفتاح؛ تحقق من نشره ثم تعامل مع المفتاح المكشوف كحادثة |
| SEC-02 | عاجلة/حرجة | القاعدة الحية: `Authenticated users can insert users` بـWITH CHECK true و`Authenticated users can delete users` بـUSING true؛ grants تسمح INSERT/DELETE | توسيع صلاحيات خطير مثبت بالإعداد. trigger منع تغيير الدور يعمل BEFORE UPDATE فقط؛ لا يحمي INSERT أو DELETE. يمكن أن يتيح انتحال ملف إداري/حذف ملفات بحسب بقية القيود؛ يثبت المسار في نسخة تجريبية |
| SEC-03 | عالية | القاعدة الحية: `Anyone can view active users` لـpublic مع SELECT لـanon؛ أعمدة users تشمل email وphone وfull_name وrole | سياسة تسمح للزائر بقراءة بيانات المستخدمين النشطين. لم تُستخرج الصفوف؛ تحقق من تعرض Data API وإغلاق الوصول غير اللازم |
| SEC-04 | عالية عند احتواء صور عملاء خاصة | `storage.buckets`: حاوية `order-images` عامة، بينما `product-images` عامة أيضًا | الرابط المعروف لملف في الحاوية العامة لا يحتاج تفويض قراءة. لم تُفتح صور؛ صنف الملفات ثم انقل الخاص بخطة تمنع كسر الطلبات والطباعة |
| SEC-05 | عالية | `src/app/api/translate-text/route.ts:17` يستدعي OpenAI دون تحقق هوية/حصة ظاهر في handler؛ مسارات إنشاء الصور والصوت تحتاج مراجعة مماثلة | خطر استهلاك خدمات مدفوعة. لم يُنفذ استدعاء مكلف؛ افحص حماية الاستضافة الخارجية قبل وصف الوصول الحي بالمؤكد |
| SEC-06 | عالية بحسب النشرة وشروط الاستغلال | lockfile: Next 15.3.6، React وReact DOM 19.1.0 | إصدارات تستدعي تحديثًا أمنيًا؛ 15.3.6 ليس محصنًا لمجرد إصلاح React2Shell القديم. نشرة ديسمبر اللاحقة تغطي ثغرات أخرى. لا تنسب له RCE القديم خطأً |
| SEC-07 | متوسطة/تتحدد بالأثر | سياسات fabrics SELECT متعددة PERMISSIVE؛ واحدة تتحقق active+available دون deleted_at، والأخرى تضيف deleted_at | السياسات المبيحة تجمع بـOR؛ الأشد لا تلغي الأوسع. احتمال إظهار محذوف منطقي ما دام يحقق شرط السياسة الأوسع؛ لم يثبت وجود صف بهذه الحالة |
| SEC-08 | تقوية لازمة | Advisors: 33 دالة search_path غير ثابت، 27 دالة SECURITY DEFINER قابلة لاستدعاء anon، و37 قابلة لاستدعاء authenticated | الأعداد متداخلة وليست 97 ثغرة مستقلة. افحص الجسم والتحقق الداخلي والاستخدام قبل إلغاء الصلاحيات |
| SEC-09 | تقوية لازمة | Advisors: حماية كلمات المرور المسرّبة غير مفعلة | تفعيلها وفق خطة المصادقة وقدرات الاشتراك، مع MFA للإدارة واختبار recovery |
| SEC-10 | جودة إطلاق | `next.config.ts` يتجاهل أخطاء الأنواع وlint أثناء build، ولا يحدد headers أمنية | ليس إثبات اختراق؛ يلزم بوابة تحقق مستقلة وفحص headers الفعلية التي قد تضيفها الاستضافة |

ملاحظات توازن مهمة: RLS مفعّل على users وfabrics وجداول المخزون التي فُحصت، وسياسات المخزون تعتمد `private.can_manage_fabric_operations()`؛ هذا لا يجعل سياسات users آمنة. كما توجد مسارات إدارية تتحقق من JWT ودور admin، فلا يصح القول إن كل API غير محمي. لدى anon/authenticated grants إضافية مثل TRUNCATE؛ لا يُستنتج منها وحدها توفر endpoint HTTP للـTRUNCATE، لكنها تستدعي إزالة الامتيازات غير المطلوبة.

أظهر Advisors أيضًا خمسة جداول RLS بلا policies: قد يكون منع الوصول المباشر مقصودًا وخاصة في schema private، وليس تسريبًا تلقائيًا. لا تضف USING true لإسكات التنبيه.

مرجع الحزم: [تحديث Next.js الأمني اللاحق لإصلاح React2Shell](https://nextjs.org/blog/security-update-2025-12-11). افحص النشرات الأحدث أثناء التنفيذ ولا تعتبر رقم إصلاح قديم «آخر إصدار آمن».

## المرحلة 1: الجرد وتثبيت خط أساس

1. سجل commit وحالة العمل، إصدارات lockfile وبيئة النشر والدومينات. اقرأ AGENTS وتعليمات المشروع. لا تمس تعديلات غير مرتبطة.
2. احصر Route Handlers وServer Actions وRPC وEdge Functions والجداول/views وStorage buckets والـjobs والربط الخارجي والمفاتيح العامة/الخاصة دون طباعة قيم الأسرار.
3. استخرج metadata للـRLS والـgrants والـtriggers والدوال SECURITY DEFINER والـsearch_path وschema exposure. الترحيل القديم ليس دليلًا على الحالة الحية.
4. ارسم مصفوفة مستخدمين: زائر، عميل أ، عميل ب، عامل، مدير ورشة، محاسب/دور تشغيل فعلي، admin، مستخدم موقوف. استخرج الأدوار الحقيقية ولا تفترض أن كل مسمى موجود في users.role.
5. جهّز نسخة اختبار وبيانات مصطنعة ونسخة احتياطية قابلة للاستعادة. حدد مسار النشر والتراجع قبل الإصلاحات التي تغير الصلاحيات.

## المرحلة 2: الاحتواء العاجل

- SEC-01: أزل تسليم المفتاح الثابت واستبدله بتفويض خادمي أو token مؤقت محدود عبر API رسمي يدعم ذلك. امنع cache والاستدعاء غير المصرح، وطابق مستهلكي endpoint حتى لا يتوقف الصوت. إذا ثبت نشر السر، دوّره لدى المزود بعد تجهيز البديل، وراجع الاستخدام والسجلات دون إعادة نشره في التقرير.
- SEC-02/03: اكتب سياسات users جديدة بأقل صلاحية وأزل السياسات الواسعة، بدل إضافة سياسات ضيقة مع إبقاء القديمة. العميل لا ينشئ صفًا بدور اختياري ولا يحذف المستخدمين. إنشاء العامل/العميل يتم عبر إجراء موثوق يثبت الدور والهوية. الملف العام، إن كان مطلوبًا، يكون projection محدود الحقول لا جدول users كاملًا.
- احمِ role وis_active والهوية على مستوى الأعمدة أو عمليات تحديث مخصصة؛ RLS ملكية الصف لا يكفي وحده لحماية جميع الأعمدة. لا تعتمد `user_metadata` على أنه مصدر صلاحيات؛ اختبر triggers إنشاء المستخدم الجديد أيضًا.
- SEC-05: تحقق موحد من جلسة المستخدم وصلاحيته في كل خدمة مدفوعة، مع rate limiting موزع وحصة/ميزانية وحجم ومدّة وامتداد مسموح، timeouts ورسائل خطأ لا تكشف أسرارًا.
- SEC-04: خطط تحويل صور الطلبات لخاص، واستبدل getPublicUrl وروابط الطباعة/العرض بروابط موقعة قصيرة العمر بعد التحقق من ملكية الطلب أو الدور. افحص الروابط القديمة والكاش؛ UUID عشوائي لا يعوض التفويض. أبقِ صور الكتالوج العامة عامة عند الحاجة.

## المرحلة 3: مراجعة التطبيق وقاعدة البيانات

- فحص IDOR/BOLA لكل معرف مستخدم وطلب وصورة ودفعة وعملية رواتب: الهوية من الجلسة والتحقق من الملكية/الدور في الخادم وقاعدة البيانات.
- مراجعة SQL injection وXSS وHTML المستخدم في الطباعة ورفع الملفات وSVG وURL fetching وSSRF وحجم الصور/audio. اختبر مدخلات غير موثوقة آمنة في البيئة التجريبية.
- فحص CORS وCSRF بحسب نمط الكوكيز/Authorization، session expiry وتسجيل الخروج والمستخدم الموقوف، حماية تسجيل الدخول واستعادة الحساب ومنع enumeration.
- مراجعة SECURITY DEFINER دالة بدالة: هل تحتاجه؟ هل تبحث عن actor موثوق؟ هل يمنع الجسم غير المصرح؟ ثبّت search_path واستخدم أسماء schema مؤهلة؛ انقل الداخلي إلى private وألغ EXECUTE غير اللازم. لا تسحب صلاحية دالة تعتمد عليها RLS دون اختبار ذلك المسار.
- views: تحقق من security_invoker والصلاحيات وRLS تحتها. التخزين: سياسات read/insert/update/delete حسب bucket والمسار والمالك وفحص محتوى الملف، وليس extension فقط.
- افحص وظائف الاستعلام بالهاتف/رقم الطلب لتجنب كشف بيانات العملاء بالتخمين، مع الحفاظ على رحلة تتبع مشروعة بتفويض مناسب.
- أصلح تضارب سياسات fabrics: سياسة عامة واحدة دقيقة تعكس active/available/deleted/hidden المعتمدة، وقراءة عامة للحقول المطلوبة فقط. يجب أن يظل موظف المخزون قادرًا على إدارته ضمن دوره.
- راجع أسرار Git history وbundles وملفات البيئة بأداة تنقيح؛ لا تضع القيم في التقرير. المفتاح anon/publishable المصمم للنشر ليس سرًا بحد ذاته؛ الحماية تعتمد RLS. service_role والمفاتيح السرية لا تصل للمتصفح.
- راجع الاعتمادات بـaudit وSCA ونشرات رسمية، مع تحليل قابلية الاستغلال والـlockfile. حدّث Next/React إلى فرع مدعوم مصحح متوافق، واختبر التطبيق بدل `audit fix --force` العشوائي.
- CSP تدريجي Report-Only ثم enforcement، وHSTS بعد تحقق HTTPS، وframe-ancestors وnosniff وReferrer-Policy وPermissions-Policy؛ توافق مع بوابة الدفع والصور والصوت. استخدم الاستجابة الحية للتحقق، لا ملف config وحده.
- فصل بيئات الاختبار والإنتاج، أسرار بأقل صلاحية، access logs منقحة، تنبيهات على الوصول الإداري والفشل المتكرر والتكلفة، نسخ احتياطية واختبار استعادة، ومراجعة وصول الفريق.

## المرحلة 4: اختبارات إثبات الإصلاح

1. قبل/بعد لكل مشكلة، بحسابات مصطنعة. المستخدم العادي لا ينشئ admin ولا يحذف المستخدمين أو يعيد تنشيط نفسه، والعميل أ لا يصل لبيانات ب، والزائر لا يرى users.
2. خدمة الصوت لا تعيد المفتاح تحت أي مسار نجاح أو خطأ؛ المستخدم المصرح يظل قادرًا على التفريغ والترجمة ضمن حصته.
3. صور الطلبات تحتاج صلاحية، الروابط الموقعة تنتهي، وصور الكتالوج تبقى قابلة للعرض. اختبر الطباعة والمعرض والموبايل.
4. اختبارات انحدار الإدارة: الدخول، إنشاء العامل، الإسناد، الطلبات، المبيعات، المخزون، الرواتب والطباعة، دون معاملات مالية حقيقية.
5. قاعدة fabrics تمنع القراءة العامة للصنف المخفي/المحذوف حتى عبر API المباشر، والإدارة تظل تعمل.
6. أعد Advisors وSCA والتحقق من headers. وثق التنبيهات المتبقية المقصودة مع سببها؛ لا تساوِ انعدام التنبيهات بالأمان الكامل.
7. بعد إضافة الدفع: اختبر التلاعب بالمبلغ والملكية، webhook المزور/replay، حجز المخزون المتزامن، والاسترداد، وفق خطة الدفع.

## شكل التقرير النهائي المطلوب

لكل نتيجة: معرف، شدة ومبرر، أصل الدليل وتاريخه، الأصل المتأثر، الشروط اللازمة، إثبات آمن منقح، سبب جذري، إصلاح محدد، اختبار قبل/بعد، الأثر الجانبي وخطة التراجع، الحالة: مؤكد/مرجح/غير منطبق/أصلح/خطر مقبول من المالك. لا تدّعِ أنه لا توجد ثغرات؛ اذكر النطاق والحدود.

معيار الإطلاق: لا نتائج حرجة/عالية قابلة للاستغلال بلا معالجة، لا أسرار في الاستجابات، عزل المستخدمين والطلبات مثبت، الخدمات المالية مقيدة ومحمية من التكرار، الاستعادة مجربة، واختبارات التدفقات الأساسية ناجحة. لا تُعالج ثغرة بإسقاط جدول أو فتح RLS أو حذف التاريخ المالي.
