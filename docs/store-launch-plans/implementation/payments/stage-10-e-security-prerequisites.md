# المرحلة 10 — استكمال متطلبات الأمان قبل أول طلب E

7 أكتوبر 2026، النسخة 1. التفويض: «اكمل الاجراءات المتبقية». **الإصلاحات محلية؛ لا نشر أو تطبيق SQL حي أو تغيير Vercel أو دفع أو فاتورة أو استرداد حقيقي.** حالة E المالية تبقى غير مكتملة. قرارات المالكة محفوظة: تجاوز شرط تجارب G3 دون PASS، الشحن 50 ريالاً شاملاً الضريبة، الرد مطفأ مؤقتاً، وإرسال الأستاذ آلياً للمبيعات الحقيقية عند تشغيل E.

## 1. النطاق والأثر

عالجنا السببين المثبتين في تحقق E السابق: الحزم القديمة SEC-06 والمسارات المدفوعة بلا تفويض SEC-05. أضفنا أيضاً حارس بدء دفع تجربة E حتى لا يفتح تشغيل الدفع لجميع الزوار قبل القرار النهائي. لا تعديل لصور التفصيل أو حاويتها؛ عمومية `order-images` ليست مانع دفع مستقلاً مثبتاً لمتجر الأقمشة.

- تثبيت `next` و`eslint-config-next` عند **15.5.27**، و`react` و`react-dom` عند **19.1.9**؛ lockfile متوافق، دون انتقال إلى Next 16. [نشرة Next.js الرسمية، 30 سبتمبر 2026](https://nextjs.org/blog/september-2026-security-release) تسمي 15.5.27 إصدار الصيانة المصحح؛ 15.3.8 المذكور في تقرير التحقق القديم ليس اختيار الإصلاح الحالي.
- حماية سبعة معالجات POST قبل قراءة الجسم أو طلب الخدمة: `translate-text`, `generate-design-prompt`, `generate-design-image`, `convert-to-cartoon`, `remove-model`, `spatial-ocr`, `transcribe-audio`.
- `requirePaidStaff` يستخدم `requireActiveStaff` القائم: خدمة Auth تتحقق من Bearer عبر `getUser`؛ ملف `users` يقرأ بعميل الخدمة؛ الدور admin/worker والنشاط يفحصان صراحة. لا اعتماد على localStorage أو claims دور من العميل. المصادقة إلزامية حتى عند إطفاء علم تحديد المعدل.
- تحديث **14 موضعاً** في ثمانية ملفات عميل بالترويسة عبر `getAuthHeader` القائم؛ الترجمة وحدها تسعة مواضع. لا تغيير نماذج الخدمات أو مخرجاتها أو تخزين النصوص. إنشاء عميل OpenAI في translate/transcribe صار بعد التفويض وفحص المفتاح بدل تحميل الوحدة.
- الأثر على المحل: الترجمة والصوت وتصميم الصور وOCR تتطلب جلسة موظف نشط. الطباعة تحتفظ ببديل النص الأصلي عند تعذر الترجمة. لا تعديل income/expenses/الرواتب/حارس المخزون/الصندوق/ترقيم الفواتير/الأستاذ أو إعادة إرسال تاريخي.

هذه معالجة للمسارات المدفوعة السبعة؛ **ليست إعلان إغلاق الخطة الأمنية 03 كاملة**. `worker-translations` مسار CRUD غير مدفوع، لا مستهلك API مباشر له في الجرد الحالي، ولم نبدل هويته أو RLS. Soniox وحراس المرحلة 4 باقية، وإعادة محاولة التفريغ المؤجلة لم تُفعّل. جرد أنواع العمال العام مستقل؛ الحارس الحالي يحافظ على admin/worker الموجودين بدلاً من اختراع صلاحيات جديدة.

## 2. تحديد معدل موزع في Supabase

الملف الجديد: [20261007100052_staff_ai_request_limits.sql](../../../../supabase/migrations/20261007100052_staff_ai_request_limits.sql). أنشئ باسم جديد بعد فحص ملفات اليوم، ولم تعدل هجرة مطبقة. تحقق الكتالوج الحي قراءةً قبل الكتابة المحلية أعاد NULL للجدول والدالة الجديدة؛ لا تطبيق حي هنا ولا `db push`.

جدول `private.staff_ai_request_limits` مع RLS وسحب صلاحية الوصول المباشر، ودالة `public.staff_ai_take_request_budget(uuid,text)` مع `search_path=''` وEXECUTE لـservice_role فقط. تفحص المستخدم النشط ودوره من جديد. قفل transaction استشاري لكل مستخدم ومجموعة ثم عدادان ذريان يمنعان تجاوز الحد عبر عدة نسخ Vercel. حدود ثابتة في SQL، لا يختارها الطلب:

| المجموعة | مساراتها | لكل 10 دقائق | لكل يوم UTC |
|---|---|---|---|
| النص | الترجمة + إنشاء الوصف | 120 | 2000 |
| الصور | إنشاء الصورة + الكرتون + إزالة الموديل | 30 | 200 |
| OCR | spatial-ocr | 60 | 500 |
| الصوت | transcribe-audio | 40 | 300 |

الحد لكل موظف، وليس لكل المتجر، ويحسب الطلب المسموح قبل طلب المزود حتى لو فشل المزود لاحقاً. هذه حدود عدد طلبات وليست ضماناً لسقف مالي أو حجم مدخلات. نافذة ثابتة وليست rolling window. التنظيف محدود بـ100 عداد قديم للمستخدم والمجموعة نفسها، دون جدول مالي أو بيانات طلبات.

`STAFF_AI_RATE_LIMIT_ENABLED` **false عند الغياب** وفق قاعدة المفاتيح الجديدة. يضبطه المالك true في Production **بعد تطبيق الهجرة** وقبل اعتماد إصلاح المعدل منشوراً. مع true: نفاد الحد يعيد 429 وRetry-After؛ الدالة الغائبة أو خطأ/نتيجة غير صالحة يعيد 503 قبل المزود، ولا يتحول تلقائياً إلى تحديد محلي أو مرور بلا حد. إطفاؤه لا يعيد فتح API للزائر، لكنه يلغي الحد الموزع، فلا يعد إغلاقاً لهذا الخطر في الإنتاج.

## 3. عزل بدء دفع تجربة E

`FABRIC_STORE_LAUNCH_ADMIN_ONLY` **false افتراضياً**؛ في نشر التجهيز وتجربة E والطوارئ يضبطه المالك **true**. في `payment/start` فقط، بعد حارسي checkout/payments وقبل قراءة الجسم أو تحميل اعتماديات ميسر، يتحقق `requireActiveStaff` ثم يشترط admin نشطاً. الزائر/الرمز غير الصالح 401؛ الحساب الموقوف/العامل/العميل 403؛ تعذر التحقق لا يبدأ دفعة.

المستهلكان: صفحة checkout و`FabricPayNowButton` في صفحات الطلب/الرجوع؛ كلاهما يرسل جلسة المتصفح الحالية. طلب الزائرة في الوضع العام بلا جلسة يبقى صالحاً عند false؛ المبلغ وكوكي الوصول والتحقق من Origin باقية كما كانت. لا مفتاح جديد في الواجهة ولا رمز سري في URL.

هذا العزل يسمح **لجميع حسابات admin النشطة**، وليس UUID مالكة واحداً. يحقق منع الدفع العام أثناء التجربة؛ إن احتاج الحساب عزل مدير واحد تحديداً فذلك قيد إضافي لم نَدّعه. إنشاء الطلب/عرض السعر يظلان متاحين، ولا تسد هذه البوابة رابط ميسر صدر سابقاً؛ لذلك يلزم التحقق من المحاولات المفتوحة قبل التبديل كما في خطة E. webhook/status/الرجوع/jobs والمطابقة لا تشترط هذا العلم أو جلسة المدير. مفتاح الطوارئ payments=false يظل صاحب الأولوية.

لا يضبط هذا العلم false للعموم إلا بتوجيه فتح صريح بعد مراجعة E. يبقى التراجع الآمن payments=false مع استمرار التحقق من القائم؛ لا حاجة لإيقاف الموقع أو مبيعات المحل.

`.next-validation` تتجاهلها Git وتفصل البناء عن خادمي المالك على 3001/3344؛ لم يوقفا. خادم التحقق المؤقت 3346 لنا فقط وأوقف بعد الفحص. تغييرات tsconfig التلقائية من Next تراجع محلياً كي لا تنشر إضافة مجلد تحقق غير لازمة.

## 5. ما ينفذه المالك الآن — بالترتيب

1. يطبق **الهجرة الجديدة فقط** أعلاه من Supabase SQL Editor، لا الهجرات القديمة ولا سكربتات db-local. التطبيق ذرّي؛ وجود تعريف سابق يوقفه ولا يكتب فوقه.
2. في Vercel، مشروع `yasmin-alsham-new2`، **Production**: يضيف `STAFF_AI_RATE_LIMIT_ENABLED=true` و`FABRIC_STORE_LAUNCH_ADMIN_ONLY=true`. تبقى payments خادم/واجهة false والرد خادم/واجهة false خلال نشر الإصلاح الأمني. لا تفعيل live أو الأستاذ تلقائياً بهذا النشر؛ قرار الأستاذ true عند حزمة تجربة E المعتمدة محفوظ.
3. ينشر الحزمة المراجعة الجديدة مع lockfile. لا يضبط `NEXT_VALIDATION_BUILD` في Vercel. نراجع بعدها READY وSHA والحزم والدالة/الصلاحيات **قراءةً**؛ النشر الذي تحققنا منه سابقاً `8a32c08…` لا يحوي هذه الإصلاحات المحلية.
4. بعد إثبات النشر والمعدل والعزل يتابع [تقرير E](stage-10-e-first-live-order.md): تسجيل دخول المدير في **المتصفح نفسه** قبل checkout، اختيار قماش/لون وكمية حقيقيين صغيرين والاستلام من المحل، وحزمة live وفق [LIVE-CONFIG.md](LIVE-CONFIG.md). السداد بيده والمبلغ عرض السعر الفعلي؛ لا أسرار ترسل في المحادثة.

لا ادعاء إغلاق G6 على الإنتاج قبل الخطوة 3 وإعادة التحقق، ولا قبول E/F قبل أدلة الطلب الحقيقي. الرد المؤجل لا يحول إلى PASS ولا يفعّل لإكمال جدول. الصور ليست عملاً مطلوباً للدفع ضمن هذا النطاق.

## 6. التراجع الآمن

- لا استعادة Next الضعيف ولا إزالة الترويسات/حراس API. الإصلاح الأمامي للإصدار المصحح أولى من العودة إلى 15.3.6.
- [staff-ai-rate-limits-rollback.sql](../staff-ai-rate-limits-rollback.sql) يسحب EXECUTE من service_role فقط، مع إبقاء `STAFF_AI_RATE_LIMIT_ENABLED=true`؛ تتوقف الخدمات المتأثرة بـ503 دون فتح استهلاك أو محو عدادات. إصلاح الدالة يكون بهجرة جديدة بعد قراءة الجسم، لا إعادة تشغيل ملف الإنشاء عند وجودها.
- تعطل بدء الدفع الخاص: payments=false، إبقاء علم الإطلاق true وباقي استقبال الدفعات كما في [RUNBOOK.md](RUNBOOK.md). لا تعطيل webhook ولا سحب إذن live أثناء وجود دفعات معلقة.
- لا reset عام أو حذف بيانات مالية أو تعديل فواتير تاريخية. العمل السابق A–D والوثائق غير المودعة محفوظ.

## 7. سجل الإكمال المحلي

نجح البناء النهائي بعد إضافة عزل الدفع وترويساته، ثم فحص HTTP عليه. اختبارات الأمان، PostgreSQL، الشحن، حساب الأسعار، والصوت أعلاه نتائج فعلية في هذا العمل، ولا نسبة نتائج إنتاج إليها. ملفات SQL الجديدة ASCII صالح لـUTF-8، والوثائق العربية تكتب UTF-8. إعادة تحقق الإنتاج بعد تطبيق المالك شرط لإغلاق خطر النشر السابق؛ لا تحديث ذاكرة دائمة أو commit أو deployment هنا.
