## 2. التصميم

### 2.1 بدء الدفع — `POST /api/fabric-store/payment/start/`
1. المفاتيح (`FABRIC_STORE_CHECKOUT_ENABLED` و`FABRIC_STORE_PAYMENTS_ENABLED`)، CSRF (نفس المرحلة 4)، كوكي الوصول.
2. `fabric_store_begin_payment` تحت قفل الطلب: الطلب `pending`/`unfulfilled` وليس تحت مراجعة؛ **محاولة مفتوحة صالحة ⇒ الرابط نفسه** (ضغطتان = فاتورة واحدة)؛ بدء آخر جارٍ منذ أقل من دقيقتين ⇒ «أعيدي بعد لحظات»؛ **نافذة الدفع = min(20 دقيقة، نهاية الحجز − دقيقتان)**، وأقل من 5 دقائق ⇒ «أعيدي إنشاء الطلب». 5 محاولات للطلب، و10 بدايات/10 دقائق لكل IP.
3. فاتورة ميسر بالمبلغ **من القاعدة**، و`expired_at` = نهاية المحاولة، و`metadata = {attempt_id, order_number}`، و`success_url`/`back_url` = صفحة رجوعنا بمعرّف المحاولة. `Origin` سبق التحقق منه، فالعنوان لا يوجَّه لموقع آخر.
4. رد ميسر يُفحص: **الرابط https على نطاق `moyasar.com`** (لا تحويل لموقع آخر)، والمبلغ والعملة مطابقان. ثم `fabric_store_attach_invoice` ⇒ `initiated`، ويحوّل المتصفح إلى صفحة ميسر.

### 2.2 مصدر الحقيقة
**لا شيء يُعتمد من المتصفح أو من جسم الـwebhook.** كل مسار (webhook، صفحة الرجوع، مهمة إعادة المعالجة) يجلب الدفعة أو الفاتورة **من واجهة ميسر بمفتاحنا**، ثم `fabric_store_apply_payment` تطابق تحت قفل الطلب ثم المحاولة: المبلغ = مبلغ المحاولة، العملة SAR، **البيئة (test/live) = بيئة المحاولة**، الفاتورة = فاتورة المحاولة. **مُختبَر:** webhook جسمه «paid» وميسر يقول «failed» ⇒ الطلب لم يُدفع.

| ما يعيده ميسر | النتيجة |
|---|---|
| `paid`/`captured` مطابق | المحاولة `paid`، الطلب `paid` (منفّذ provider)، **مهمة `confirm_order` واحدة** (مفتاح فريد). حارس المرحلة 2 يرفع المراجعة إن لم يبقَ حجز سارٍ |
| نفسه مرة ثانية (webhook مكرر، صفحة الرجوع، إعادة معالجة) | `already_paid` — لا أثر |
| `paid` على طلب مسدَّد بمحاولة أخرى | `overpaid`: الأولى تبقى، الطلب للمراجعة، مهمة `notify_staff` — **لا شحنتان** |
| `paid` على طلب ملغى | يُسجَّل السداد + مراجعة (دفعة حقيقية لا تُرفض) |
| غير مطابق (مبلغ/عملة) | `quarantined`: لا اعتماد، الطلب للمراجعة، `notify_staff` |
| `failed` | المحاولة `failed` (إن لم تُدفع)؛ الطلب يبقى قابلاً للدفع بفاتورة جديدة. **لا يعود paid إلى failed** |
| `authorized`/`verified`/`initiated` | يُسجَّل للاطلاع فقط — التفويض ليس تحصيلاً |
| `refunded`/`voided` على محاولة مدفوعة | `quarantined` + مراجعة (استرداد خارج النظام؛ المرحلة 8) |
| فاتورة لا تخص محاولة (أو بيئة أخرى) | `unknown` ⇒ محجور للمطابقة (المرحلة 9) |

### 2.3 الانقطاع أثناء إنشاء الفاتورة (لا مفتاح عدم تكرار لدى ميسر)
- **رفض 4xx أو انقطاع/مهلة:** تُغلق المحاولة `cancelled` (`create_rejected`/`create_unknown`). الزبونة لم ترَ رابطاً، فلا دفع ممكن على فاتورة قد تكون أُنشئت؛ وستنتهي مدتها وحدها.
- **تعطّل الخادم بعد إنشاء الفاتورة وقبل ربطها:** المحاولة تبقى `created`. إن وصلت دفعة على تلك الفاتورة، يجلب الخادم الفاتورة ويأخذ `metadata.attempt_id` ويربط — **فقط** بمحاولة بلا فاتورة، ومطابقة المبلغ تبقى. **مُختبَر من طرف لطرف.** الضغطة التالية بعد دقيقتين تغلق المحاولة العالقة وتفتح جديدة.

### 2.4 الـwebhook — `POST /api/payments/moyasar/webhook/`
1. الجسم ≤ 64KB وJSON بالشكل المتوقع (وإلا 400).
2. `MOYASAR_WEBHOOK_SECRET` غير مضبوط ⇒ 503 (يعيد ميسر المحاولة). السر خاطئ ⇒ **401 ولا يُحفظ شيء** (مقارنة بزمن ثابت).
3. **يُحفظ الحدث أولاً** بمعرّفه لدى ميسر (فريد لكل بيئة)، **منقَّحاً**: بلا اسم حامل البطاقة ولا الرقم المقنّع ولا معرّفات البوابة ولا السر (مُختبَر). فشل الحفظ ⇒ 500 فيعيد ميسر الإرسال.
4. من هنا **200 دائماً**: حدث مكرر معالَج ⇒ لا شيء؛ بيئة مختلفة أو نوع غير مدعوم ⇒ محجور؛ وإلا تُجلب الدفعة ويُطبَّق. ميسر لا يرد أثناء المعالجة ⇒ الحدث `failed` وتعيده المهمة (مُختبَر). بعد 10 محاولات ⇒ محجور.
5. لا يتبع مفتاح «الدفع الجديد»: دفعة بدأت قبل الإطفاء تُعتمد (نص الخطة).

### 2.5 صفحة الرجوع — `/fabrics/payment/return/?attempt=…`
الصفحة لا تقرأ شيئاً من الرابط سوى معرّف المحاولة. تسأل `GET /api/fabric-store/payment/status/` كل 3 ثوانٍ لنحو دقيقة. الخادم يتحقق أن المحاولة **تخص طلب الكوكي**، وإن حان الوقت (مرة كل 10 ثوانٍ على الأكثر، يُحجز الدور ذرياً) يجلب الفاتورة ويطبّق دفعاتها — **فيكتمل الطلب ولو لم يصل webhook** (مُختبَر). 120 استعلاماً/10 دقائق لكل IP. **السلة تُفرَّغ بعد السداد الموثّق فقط.** «رجوع» من ميسر ⇒ «لم يكتمل الدفع» مع إعادة المحاولة ما دام الحجز قائماً.

## 8. التراجع

**أولاً أطفئي `FABRIC_STORE_PAYMENTS_ENABLED`** (يتوقف بدء الدفع؛ الـwebhook وصفحة الرجوع يستمران لما بدأ). انتظري انتهاء صفحات الدفع المفتوحة (20 دقيقة على الأكثر). ثم:

```sql
begin;

set local lock_timeout = '5s';

-- قفل المحاولات قبل الفحص (لا تُفتح صفحة دفع بين الفحص والحذف). NOWAIT: إن كان
-- بدء دفع جارياً الآن ينسحب التراجع فوراً ويُعاد لاحقاً.
lock table public.fabric_store_payment_attempts in share row exclusive mode nowait;

do $$
begin
  if exists (
    select 1 from public.fabric_store_payment_attempts
    where status in ('created', 'initiated', 'authorized') and expires_at > now()
  ) then
    raise exception 'ROLLBACK REFUSED: a payment page is open (a customer may be paying now). Switch FABRIC_STORE_PAYMENTS_ENABLED off, wait for open attempts to expire (at most 20 minutes), then retry.';
  end if;
end $$;

-- المحاولات والأحداث بيانات المرحلة 2 وتبقى (سجلات مالية). تُحذف الدوال فقط.
drop function public.fabric_store_begin_payment(bytea, text, bytea);
drop function public.fabric_store_attach_invoice(uuid, text, text);
drop function public.fabric_store_abandon_attempt(uuid, text, text);
drop function public.fabric_store_record_payment_event(text, text, text, text, text, text, jsonb);
drop function public.fabric_store_apply_payment(uuid, text, jsonb, uuid);
drop function public.fabric_store_note_event_failure(uuid, text, boolean);
drop function public.fabric_store_pending_payment_events(integer);
drop function public.fabric_store_payment_view(bytea, uuid, bytea);

commit;
```

بعد التراجع يرد الـwebhook بخطأ فيعيد ميسر المحاولة ثم يُسقط؛ **لا تتراجعي بعد أول دفعة حقيقية** — أطفئي المفتاح فقط (الخطة: «لا توقف webhook كطريقة تراجع»). الترتيب: 5 ← 4 ← 3 ← 2.

## 9. ما أطلب من المراجع

1. **مصدر الحقيقة (§2.2):** هل يوجد مسار يعتمد سداداً دون جلبه من ميسر؟
2. **الاستعادة بـmetadata (§2.3):** هل يمكن لمهاجم أن يجعل دفعة على فاتورته تسدد طلب غيره؟ (metadata تُقرأ من فاتورة مجلوبة بمفتاحنا؛ الربط لمحاولة بلا فاتورة فقط؛ المبلغ يُطابَق.)
3. **الـwebhook (§2.4):** رفض السر الخاطئ بلا حفظ مقابل الحفظ للتدقيق — أيهما أصح؟ وهل 200 بعد الحفظ مع فشل المعالجة صحيح بوجود المهمة؟
4. **صفحة الرجوع (§2.5):** هل الحد (مرة/10 ث + 120/10 د) يكفي لمنع استعمالها لإغراق ميسر بطلبات؟
5. **السقوف الزمنية (§2.1):** صفحة الدفع تنتهي قبل الحجز بدقيقتين. دفعة تكتمل في آخر ثانية ويصل تأكيدها بعد انتهاء الحجز ⇒ مدفوع + مراجعة (مُختبَر). هل يكفي؟
6. **لا يوجد اعتماد من المتصفح:** هل فاتني مسار يثق بمعامل في رابط الرجوع؟
