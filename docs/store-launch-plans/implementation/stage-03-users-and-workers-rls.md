## 3. إصلاح الكود — النهج الصحيح

### 3.1 لماذا أُلغي نهج النسخة 2

`{ global: { headers: { Authorization: 'Bearer …' } } }` كان يحلّ الاعتماد على سياسة القراءة، لكنه **استبدل شرطاً ضمنياً بلا شرط**، فأدخل قبول الحساب الموقوف (أعلاه).

### 3.2 النهج المعتمد — موجود في الكود أصلاً

`alostaz/send-fabric-invoice` يطبّق النمط الصحيح، وتعليقه يشرحه:

> «نستخدم عميل الخادم بعد التحقق من التوكن حتى لا يعتمد قرار الصلاحية على سياسات القراءة العامة»

اعتمدتُ هذا النمط في المسارات التسعة كلها:

```js
const { data: userData, error: roleError } = await supabaseAdmin   // عميل الخدمة
  .from('users')
  .select('role, is_active')                                      // النشاط صراحةً
  .eq('id', user.id)
  .single()

if (roleError || !userData?.is_active) return 403                  // الموقوف يُرفض
if (userData.role !== 'admin')        return 403
```

**ثلاث خصائص:** قرار الصلاحية **لا يعتمد على أي سياسة RLS** فلا يتأثر بأي ترحيل لاحق · **فحص النشاط صريح** لا ضمني · خطأ القراءة يُرفض صراحةً (`roleError`) بدل المرور صامتاً.

`update-credentials` احتاج ترتيباً إضافياً: عميل الخدمة كان يُنشأ **بعد** فحص الدور، فنُقل قبله مع حارس متغيّر البيئة، وحُذف التعريف المكرر.

## 4. حارس العمال

### 4.1 خطأ النسخة 1

`SECURITY DEFINER` + استثناء `current_user IN ('postgres', …)`. الدوال مملوكة لـ`postgres` (تحقّقنا من `pg_proc.proowner`)، و`current_user` داخل `DEFINER` هو **المالك**، فالشرط يتحقق دائماً → **الحارس لا يفحص شيئاً**.

### 4.2 التصميم

`SECURITY INVOKER` (لا يحتاج صلاحية مرتفعة؛ `is_admin()` نفسها `DEFINER`) + ادعاء الـJWT بدل `current_user` كمصدر لهوية الطلب.

> **حدّ صريح (ملاحظة المراجع 3):** `INVOKER` يمنع تلوّث الفحص بهوية *مالك الدالة* كما حدث في النسخة 1، **لكنه لا يثبت دائماً هوية المستخدم الأصلي**: إن وصل التحديث عبر دالة أخرى `SECURITY DEFINER` فقد يرث سياقها المرتفع. لذلك **يجب اختبار الاستدعاء المباشر والمتداخل** قبل الاعتماد. لا تعامل `INVOKER` كإثبات هوية.

### 4.3 استثناء الصيانة — قُيّد

النسخة 2 كانت: `IF claims IS NULL THEN RETURN NEW` — أي أن **أي** اتصال بلا سياق HTTP يمرّ. والمراجع محقّ: غياب الـJWT لا يثبت التخويل.

```sql
IF claims IS NULL OR claims = '' THEN
  IF current_user IN ('postgres', 'supabase_admin') THEN RETURN NEW; END IF;
  RAISE EXCEPTION 'Protected worker columns cannot be changed without a trusted context (role: %)', current_user;
END IF;
```

مع `SECURITY INVOKER` يكون `current_user` هو المستدعي فعلاً — فالفحص هنا سليم، بعكس النسخة 1.

**أثره على الاختبار:** الاختبار عبر `psql` **ممكن وصحيح** إن ضُبط الدور وادعاءات مستخدم مصطنع (`SET LOCAL role authenticated` + `SET LOCAL request.jwt.claims`). بلا ذلك السياق لا يمثّل الاختبار عاملاً حقيقياً. الأداة ليست المشكلة، بل السياق.

### 4.4 عيب تصميم صحّحه المراجع — الحارس كان يرفض أكثر مما يلزم

النسخة 3 فحصت السياق **قبل** أن تسأل هل تغيّر عمود محمي. فأي تحديث من دور غير مستثنى وبلا سياق طلب كان يُرفض — **حتى لو لم يقترب من عمود محمي إطلاقاً**. أي أن مهمة صيانة تحدّث `bio` أو `is_available` أو خدمة تحدّث `performance_rating` كانت ستتعطل بلا سبب.

أُعيد ترتيب الحارسين إلى ثلاث خطوات:

```
1. هل تغيّر عمود محمي؟  لا  →  RETURN NEW فوراً، مهما كان السياق.
2. نعم  →  هل السياق موثوق؟ (service_role / admin / دور صيانة محدد)
3. سياق غير مخوّل يغيّر عموداً محمياً  →  EXCEPTION
```

الحارس صار يضيق على **الأعمدة المحمية وحدها**، وكل التحديثات العادية تمرّ من أي سياق. وهذا أيضاً يقلّص سطح الاختبار: لا حاجة لجرد كل مهام الصيانة، يكفي جرد ما يمسّ `worker_type` و`hourly_rate` و`user_id` (و`is_active` في حارس users).

أُضيف اختبار مقابل: **تحديث عادي من نفس السياق يجب أن ينجح.**

### 4.5 تعليقان قديمان صُحّحا

| الموضع | كان | صار |
|---|---|---|
| ملف العمال | «اختبر عبر API لا عبر psql» | psql صحيح بشرط ضبط `role` و`request.jwt.claims` — مع مثال جاهز |
| ملف المستخدمين | «أي 403 يعني أن الكود غير منشور» | افحص بالترتيب: حساب موقوف (**رفض مشروع**) ← دور غير admin ← الكود غير منشور |

الثاني كان سيقود إلى تشخيص خاطئ: بعد تشديد البوابة صار الحساب الموقوف **سبباً مشروعاً** للرفض.

> **فخّ كامن مسجَّل:** `prevent_role_change` القائم على `users` لا يتضمن استثناء `service_role`، و`is_admin()` تعيد `false` لمفتاح الخدمة — فأي مسار خادمي يحدّث `users.role` سيُرفض. لم أجد مساراً كهذا، ولم أعدّلها.

## 5. الأثر الجانبي

### 5.1 ما لا يتغيّر

الرواتب والحضور · المدير **النشط** يدير العمال والمحاسبة · إنشاء العامل وحذفه · العامل يعدّل اسمه وهاتفه · **تتبّع الطلبات — لم يُمسّ جدول `orders`** · الأقمشة والمخزون والطباعة.

### 5.2 ما يتغيّر

زائر يقرأ `users`/`workers`: 25/19 ← **0/0** · حذف أو إدراج صف مستخدم: ممكن ← مرفوض · **تغيير `worker_type` أو `hourly_rate` ذاتياً**: ممكن ← استثناء · موقوف يعيد تنشيط نفسه: ممكن ← استثناء · **مدير موقوف في بوابات API**: يمرّ ← **يُرفض**.

### 5.3 أخطر ما قد ينكسر

1. **مدير موقوف بالخطأ** (`is_active = false` سهواً) يُرفض في كل المسارات. تشديد مقصود، لكنه قد يُقرأ كعطل. **العلاج تفعيل الحساب، لا التراجع.**
2. **رفض مسار خادمي في الحارس** إن أخفق استثناء `service_role` (§4.3).
3. **دور إداري غير `admin`** يحتاج تغيير `worker_type`. لم أجده، **ولم يُجرَد**.

### 5.4 حدّ صريح: احتواء جزئي

`TO authenticated` يشمل العملاء المسجّلين والحسابات الموقوفة التي تحمل رموزاً صالحة.

> **يُغلق القراءة أمام الزائر غير المسجّل. القراءة بين الأدوار تبقى خطراً مسجَّلاً.**

التضييق النهائي يحتاج **جرد الصلاحيات (المرحلة 0)** — أهمّ نقص في المشروع الآن.

## 7. التراجع

**القاعدة:** عالج المسار المتعطل تحديداً، أو قيّد العملية المتأثرة في طبقة التطبيق — **مع إبقاء المنع قائماً في القاعدة**.

| العطل | العلاج الصحيح | ❌ ممنوع |
|---|---|---|
| 403 في مسار | تحقق أن الحساب نشط؛ ثم انشر إصلاح الكود | إعادة `Anyone can view active users` |
| الحارس يمنع مساراً مشروعاً | **`CREATE OR REPLACE` داخل معاملة** | `DROP TRIGGER` |
| دور مشروع فقد قراءة | سياسة إضافية دقيقة لذلك الدور | العودة إلى `TO public` |

**تصحيح على النسخة 2 (ملاحظة المراجع 4):** كنت أعرض `DROP TRIGGER` كخيار أضيق. **خطأ** — بين الإسقاط وإعادة التركيب نافذة تصعيد مكشوفة، و«أعد تركيبه لاحقاً» ليس خطة. البديل `CREATE OR REPLACE FUNCTION` داخل معاملة واحدة: الجسم يُستبدل ذرّياً والمشغّل يبقى مركّباً، **فلا لحظة واحدة بلا حماية**. حُدّث في ملفَي الـSQL.

**وحُذف** من النسخة 2 قولي «تراجَع عن الجزء أ أولاً ثم الكود» — كان يناقض منع إعادة السياسات المفتوحة. إصلاح الكود مستقل ولا يحتاج تراجعاً عند التراجع عن SQL.

**لا تستعد نسخة احتياطية كاملة لعلاج عطل صلاحيات.**

## 8. ما أطلب من المراجع

1. **أعد اختبار بوابة التفويض بحساب مدير موقوف** — هل أُغلق التراجع فعلاً في المسارات التسعة؟
2. **هل نقل قراءة الدور إلى عميل الخدمة يفتح أي مسار جديد؟** الفحص لم يعد يمرّ بـRLS إطلاقاً، فصحّته تقع كلها على `roleError` و`is_active` و`role`.
3. **راجع ترتيب `update-credentials`** — نقل إنشاء عميل الخدمة وحارس متغيّر البيئة قبل فحص الدور.
4. **تحقّق من §4.3**: هل `current_user` سليم الآن مع `SECURITY INVOKER`، وهل `('postgres','supabase_admin')` هي القائمة الصحيحة لهذا الإعداد؟
5. **هل `current_setting('request.jwt.claims', true)` يعكس `service_role` فعلاً** لمفتاح الخدمة؟ آخر نقطة فشل غير مختبَرة.
6. **لا تعتبر أي نتيجة هنا تحققاً من الحالة بعد التطبيق.**
