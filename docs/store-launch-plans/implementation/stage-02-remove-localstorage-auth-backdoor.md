## 2. الآلية الدقيقة

```js
// authStore.ts — قبل
const defaultUsers = [{
  id: '1',
  email: 'admin@yasminalsham.com',
  password: 'admin123',
  role: 'admin' as const,
  is_active: true
}]
localStorage.setItem('yasmin-users', JSON.stringify(defaultUsers))
```

الاستدعاء الأول لـ`getStoredUsers()` **يزرع** الحساب إن لم يكن موجوداً. ثم في `signIn`، بعد أي فشل من Supabase:

```js
const foundUser = users.find(u =>
  u.email.toLowerCase() === email.toLowerCase() && u.password === password
)
if (foundUser) {
  set({ user, isLoading: false, error: null, lastVerifiedAt: Date.now() })
  return true      // ← جلسة «ناجحة» بلا أي تحقق خادمي
}
```

ثلاث مشكلات متراكبة: بيانات اعتماد ثابتة في الحزمة المشحونة للمتصفح، ومقارنة كلمة مرور نصية، و`lastVerifiedAt: Date.now()` الذي يجعل `isSessionFresh()` تعيد `true` لخمس دقائق فيُتخطّى التحقق في صفحة الدخول.

## 3. تقدير الخطورة — بدقة، وبلا تهويل

**الكود المحلي** يتضمن حارساً يتحقق من الجلسة عند تهيئة Supabase: `DashboardSessionBoundary` يغلّف `src/app/dashboard/layout.tsx` كاملاً — أي كل مسارات اللوحة في هذه النسخة — ويستدعي `supabase.auth.getUser()`، وهو تحقق خادمي، ثم يعيد قراءة الدور من جدول `users`. فمن دخل عبر المسار الاحتياطي لا يملك جلسة Supabase، ويُتوقَّع أن يُمسح كاشه ويُعاد إلى صفحة الدخول.

**حدود هذا الاستنتاج — ثلاثة قيود صريحة:**

1. **لم تُراجع النسخة المنشورة.** ما سبق قراءة للكود المحلي فقط. لا أعرف ما هو مبنيّ ومنشور فعلاً في الإنتاج.
2. **لم تُراجع سجلات الاستغلال.** لا يوجد أي دليل ينفي أن الباب استُخدم. غياب الدليل ليس دليل غياب.
3. **حارس الواجهة لا يثبت حماية الطبقات الأدنى.** هو مكوّن عميل؛ لا يحمي مسارات API ولا قاعدة البيانات. من يحمل ملفاً محلياً بدور admin **لا** يكتسب صلاحيات قاعدة بيانات (تلك تُشتق من `auth.uid()`)، لكن إثبات ذلك يقع على سياسات RLS — وهي موضوع المرحلة 3، وفيها ثغرات مؤكدة لم تُغلق بعد.

**التصنيف الدقيق:** المسار كان يمنح جلسة عميل بلا تحقق خادمي. كلفة إبقائه كانت صفراً لأنه لم يقدّم وظيفة حقيقية (§5.2)، وخطره يرتفع دفعةً واحدة مع خطأ نشر واحد.

**الخطر الحقيقي شرطي، لا فوري.** كل الحمايات أعلاه معلّقة على `isSupabaseConfigured()`. وهي تقرأ `NEXT_PUBLIC_*`، أي قيم **تُخبز وقت البناء** لا وقت التشغيل. فإذا بُني الموقع ونُشر بمتغيرات بيئة ناقصة أو نائبة، تنقلب الحالة دفعةً واحدة:

| المكوّن | سلوكه عند `!isSupabaseConfigured()` — قبل الإصلاح |
|---|---|
| `signIn` | يقبل `admin123` وينشئ جلسة admin |
| `DashboardSessionBoundary` | يمنح اللوحة من الكاش بلا تحقق |
| `login/page` | يوجّه إلى اللوحة مباشرة |
| `DeleteOrderModal` | يقبل كلمة المرور من `localStorage` |

**النتيجة: لوحة الإدارة كاملة تُفتح بكلمة مرور ثابتة منشورة في الكود.** ولا يُصدر النظام أي إشارة — يبدو سليماً تماماً.

**التصنيف الدقيق:** ليست ثغرة مستغَلة اليوم. هي **مفتاح انهيار كامن** يقلبه خطأ نشر واحد، وقد بقي قائماً بلا مبرر لأن المسار لم يكن يقدّم أي وظيفة حقيقية (§5.2).

## 4. التغييرات

### 4.1 `authStore.ts` — حذف مخزن بيانات الاعتماد

حُذفت `getStoredUsers` بالكامل (25 سطراً) واستُبدلت بتعليق يوثّق سبب الإزالة.

### 4.2 `authStore.ts` — `signIn` بلا مسار احتياطي

```js
if (!isSupabaseConfigured()) {
  set({ error: 'تعذّر الاتصال بخادم المصادقة. يرجى مراجعة مسؤول النظام.', isLoading: false })
  return false
}
set({ error: 'بيانات تسجيل الدخول غير صحيحة...', isLoading: false })
return false
```

رسالتان متمايزتان: **عطل تهيئة** يوجّه لمسؤول النظام، و**بيانات خاطئة** للمستخدم. الثانية لا تفرّق بين بريد غير موجود وكلمة مرور خاطئة، فلا تتيح حصر الحسابات (enumeration).

تتبّع كل الحالات:

| الحالة | قبل | بعد |
|---|---|---|
| مهيأ + نجاح + ملف موجود | `true` | **`true` — بلا تغيير** |
| مهيأ + نجاح + ملف مفقود | خطأ، `false` | **بلا تغيير** (يعود مبكراً) |
| مهيأ + فشل مصادقة | ← المسار الاحتياطي | خطأ «بيانات غير صحيحة»، `false` |
| غير مهيأ | ← المسار الاحتياطي | خطأ تهيئة، `false` |

حُذف أيضاً `await new Promise(r => setTimeout(r, 1000))` — تأخير صناعي كان داخل المسار المحذوف. أثره الوحيد أن رفض الدخول صار أسرع.

**تصحيح سجل مضلّل (ملاحظة المراجع هـ):** بقي بعد فشل مصادقة Supabase تعليق وسجل يقولان `⚠️ التحول إلى localStorage...` رغم زوال المسار. كانا سيوجّهان أي تشخيص مستقبلي إلى مسار غير موجود. استُبدلا بتعليق يصف السلوك الفعلي: السقوط إلى رسالة الخطأ في نهاية الدالة. **تغيير في التشخيص فقط، بلا أثر سلوكي.**

### 4.3 `DashboardSessionBoundary.tsx` — الأهم أمنياً

```js
if (!isSupabaseConfigured()) {
  console.error('Supabase غير مهيأ — تعذّر التحقق من الجلسة')
  clearCachedUser()
  router.replace(getLoginUrl())
  return
}
```

هذا هو التغيير الذي يُبطل الانقلاب الموصوف في §3: لم يعد غياب التهيئة يفتح اللوحة، بل يغلقها. `clearCachedUser` معرّفة على مستوى الوحدة (السطر 50) ومستخدمة في أربعة مواضع أخرى — لم أُنشئ شيئاً جديداً.

حُذف `const cachedUser = ...` لأنه لم يعد مقروءاً في أي موضع (تُحقق بالبحث: كان استخدامه الوحيد داخل الفرع المحذوف).

### 4.4 `DeleteOrderModal.tsx` — يفشل مغلقاً

تأكيد كلمة المرور قبل حذف الطلب عبر Supabase حصراً. **رسالة الخطأ للمستخدم لم تتغيّر** (`t('incorrect_password')`) — التغيير في المسار لا في التجربة.

### 4.5 `login/page.tsx` — منع الارتداد

لولا هذا التعديل لحدث ارتداد: صفحة الدخول توجّه للوحة، والحارس يعيد فوراً. لا حلقة لانهائية — `clearCachedUser` كانت ستنهيها بعد دورة واحدة — لكنها وميض مربك بلا فائدة. الآن المنطق متسق في الطرفين.

## 5. ما فحصته ولم أغيّره

### 5.1 `dataStore.ts` — كود ميت يكتب كلمات مرور نصية

`addWorker` و`updateWorker` و`deleteWorker` تكتب `{ email, password }` نصاً في `yasmin-users`.

**تحققت: الملف غير مستورد في أي مكان.** `grep -rn "from '@/store/dataStore'" src/` لا يُرجع شيئاً. وصفحة العمال تستخدم `useWorkerStore` الذي يمرّ عبر `/api/workers/*` بـ`service_role`. فهذه الدوال **لا تُنفَّذ إطلاقاً**، ولا يوجد تعرّض حيّ.

**لم أحذفه.** حذف ملف كامل توسيع لنطاق مرحلة موضوعها المصادقة، وأثره أوسع من فائدته الآن. **موصى به كتنظيف مستقل**، وهو الآن المرجع الوحيد المتبقي لـ`yasmin-users` في `src/`.

### 5.2 هل فقدنا وظيفة «وضع التطوير»؟

لا. عند `!isSupabaseConfigured()` لا يوجد اتصال بقاعدة البيانات أصلاً: لا طلبات، ولا عمال، ولا أقمشة، ولا رواتب. المسار الاحتياطي كان يمنح **واجهة فارغة** تبدو كأنها تعمل. لا وظيفة حقيقية فُقدت.

**أثر على المطورين:** من يشغّل المشروع بلا `.env.local` لن يستطيع الدخول. هذا هو السلوك الصحيح.

### 5.3 مفاتيح `localStorage` — تمييز لازم

| المفتاح | الدور | الحالة |
|---|---|---|
| `yasmin-users` | **مخزن بيانات اعتماد** (بريد + كلمة مرور نصية) | **لم يعد يُقرأ من أي مسار حيّ** |
| `yasmin-auth-user` | كاش ملف الجلسة، بلا كلمة مرور | **باقٍ — مشروع وغير ممسوس** |
| `yasmin-auth-storage` | تخزين Zustand المستمر | **باقٍ — غير ممسوس** |
| **`sb-qbbijtyrikhybgszzbjz-auth-token`** | **جلسة Supabase الحقيقية** | **باقٍ — غير ممسوس. هذا ما يُبقي المستخدمين داخلين** |

الخلط بينها كان سيكسر الجلسات. الأول فقط هو المستهدف.

### 5.4 بقايا `yasmin-users` على الأجهزة — ليست بالضرورة غير ضارة

النسخة 1 وصفت البقايا بأنها «غير ضارة». **تصحيح:** إيقاف القراءة يمنع استخدامها، **لكنه لا يمحوها**. المفتاح يبقى على كل جهاز زُرع فيه.

**ما يحتويه:** في الحد الأدنى حساب admin الافتراضي بكلمة مروره الثابتة. وقد يحتوي **أكثر**: `dataStore.ts` (§5.1) يكتب `{ email, password }` نصاً لكل عامل يُضاف أو يُحدَّث. هو ميت اليوم، **لكن عدم استيراده الآن ليس إثباتاً تاريخياً أنه لم يُستخدم قط**. فقد تحمل أجهزة قديمة بيانات اعتماد عمال حقيقية بنص صريح.

**مهمة تنظيف مستقلة — موصى بها بعد اعتماد هذه المرحلة:**

1. امسح المفتاح `yasmin-users` **وحده** على كل جهاز يستخدمه الفريق (أدوات المطور ← Application ← Local Storage). **لا تمسح `localStorage` كاملاً** — ذلك يمسح `sb-…-auth-token` فيُخرج المستخدم من جلسته.
2. إن ثبت أنه احتوى كلمات مرور عمال فعلية، فالمعالجة الصحيحة **تدوير تلك الكلمات**، لا مسح المفتاح وحده.
3. يمكن إضافة مسح لمرة واحدة عند الإقلاع (`localStorage.removeItem('yasmin-users')`) لتغطية الأجهزة التي لا تُراجَع يدوياً. **لم أضفه** — تغيير سلوكي خارج نطاق هذه المرحلة، ويحتاج قراراً منفصلاً.

## 6. تحليل الأثر الجانبي

### 6.1 هل يُخرج أحداً من جلسته؟

**لا** — بشرط أن تكون متغيرات البيئة مضبوطة في بناء الإنتاج.

كل المسارات المعدّلة داخل فروع `!isSupabaseConfigured()`، وهي فروع **لا تُنفَّذ** في الإنتاج المهيأ. المسار الوحيد المعدّل خارجها هو نهاية `signIn`، ولا يُبلغ إلا بعد فشل مصادقة Supabase — وهو مسار كان ينتهي بالفشل أصلاً ما لم تُستخدم بيانات الباب الخلفي.

**تصحيح — أين تُخزَّن الجلسة فعلاً:** النسخة 1 قالت «تحملها كوكيز Supabase». **هذا خطأ.** `createClient` في `src/lib/supabase.ts` يُستدعى بـ`persistSession: true` وبلا `storage` مخصص، فيستخدم التخزين الافتراضي للمتصفح وهو **`localStorage`** تحت مفتاح `sb-qbbijtyrikhybgszzbjz-auth-token` — لا كوكيز.

**النتيجة لا تتغيّر، لكن سببها يتغيّر ويجب أن يكون دقيقاً:** الجلسات تبقى لأن هذا المفتاح **ليس من المفاتيح التي مسّها التغيير** (§5.3)، لا لأنها خارج `localStorage`. والتمييز عملي: من يمسح `localStorage` كاملاً أثناء الاختبار **سيُخرج نفسه من الجلسة** ويظن أن التغيير طرده.

### 6.2 ما تغيّر سلوكياً

| الحالة | قبل | بعد |
|---|---|---|
| دخول صحيح، Supabase مهيأ | ينجح | **بلا تغيير** |
| دخول خاطئ، Supabase مهيأ | خطأ بعد تأخير ثانية | خطأ فوري |
| دخول بـ`admin123` | **ينجح في واجهة الدخول** | يفشل |
| Supabase غير مهيأ | واجهة فارغة تبدو عاملة | منع دخول برسالة واضحة |

### 6.3 ما لم يتغيّر

`signOut` · `checkAuth` · `setUser` · `setUserWithTimestamp` · `isAuthenticated` · `isSessionFresh` · تخزين Zustand · كل مسار التحقق الخادمي في `DashboardSessionBoundary` · رسائل الخطأ المرئية في `DeleteOrderModal` · كل ملف آخر في المشروع.

## 7. شرط النشر — حرج

`isSupabaseConfigured()` تقرأ `NEXT_PUBLIC_*`، وهي قيم **تُخبز وقت البناء**. فبناءٌ تنقصه هذه القيم يُنتج تطبيقاً **لا يستطيع أحد الدخول إليه** — قبل الإصلاح كان يُنتج تطبيقاً **يدخله الجميع بكلمة مرور ثابتة**.

الثاني أسوأ بما لا يقاس، والأول عطل صاخب يُكتشف فوراً. لكنه يظل عطلاً كاملاً.

**قبل النشر، تحقّق من وجود القيمتين في بيئة الإنتاج (Vercel)، لا في `.env.local` فقط:**

```
NEXT_PUBLIC_SUPABASE_URL
NEXT_PUBLIC_SUPABASE_ANON_KEY
```

**ما تحققت منه:** وجود المفتاحين في `.env.local` المحلي بقيم غير نائبة (فحصت أسماء المفاتيح فقط، **لم أطبع أي قيمة**؛ تطابق «placeholder» وقع على سطر تعليق لا على قيمة).
**ما لم أتحقق منه:** بيئة الإنتاج. لا أملك وصولاً إليها، **والمحلي ليس دليلاً على الإنتاج.**

### 7.1 التعافي عند غياب المتغيرات — يتطلب إعادة بناء

**تصحيح على النسخة 1.** قيم `NEXT_PUBLIC_*` **تُخبز داخل الحزمة وقت البناء**. لذلك ضبط المتغير في لوحة الاستضافة **لا يُصلح حزمة مبنية سابقاً** — الحزمة المنشورة تحمل القيمة القديمة (أو غيابها) محفورة فيها.

خطة التعافي الصحيحة، بالترتيب:

1. اضبط `NEXT_PUBLIC_SUPABASE_URL` و`NEXT_PUBLIC_SUPABASE_ANON_KEY` في بيئة الإنتاج.
2. **أعد البناء** — لا يكفي إعادة التشغيل أو ترقية نشر قائم.
3. **أعد النشر** من البناء الجديد.
4. **تحقق من الدخول فعلياً** بحساب حقيقي قبل اعتبار العطل منتهياً.

تخطّي الخطوتين 2 و3 يُنتج تشخيصاً خاطئاً: المتغير يبدو مضبوطاً في اللوحة والتطبيق ما زال يمنع الدخول.

## 9. التراجع

```bash
git diff                # راجع أولاً
git revert <hash>       # بعد الإيداع — المفضّل
```

**تحذير مستمر من مراجعة المرحلة 1:** `git checkout -- <file>` يمحو **كل** التعديلات غير المودعة في الملف. لا تستخدمه إلا بعد `git diff` والتأكد. الأأمن: الإيداع ثم `git revert`.

**التراجع هنا أثقل من المرحلة 1: أربعة ملفات، وأحدها مسار تسجيل الدخول.**

**قيد مطابق لقاعدة §7.3 في المرحلة 1: لا يُتراجع عن إغلاق ثغرة مصادقة لإصلاح عطل وظيفي.** إن ظهر عطل دخول بعد النشر:

1. **تحقق أولاً من متغيرات بيئة الإنتاج** (§7). هذا هو السبب الأرجح بفارق كبير، وعلاجه **ضبط المتغير ثم إعادة البناء والنشر** (§7.1) — لا التراجع. ضبط المتغير وحده لا يكفي.
2. إن ثبت أن السبب تغيير آخر في هذه المرحلة، تراجع عنه **وحده**.
3. **ممنوع:** إعادة المستخدم الافتراضي أو مقارنة كلمة المرور النصية كحلّ سريع.

## 10. ما أطلب من المراجع

الملاحظات الخمس السابقة عولجت — أربع في الوثيقة وواحدة في الكود. المفتوح الآن:

2. **راجع §5.4**: هل توصيف بقايا `yasmin-users` صار كافياً، وهل تأجيل المسح التلقائي عند الإقلاع قرار سليم أم يجب أن يسبق الاعتماد؟
3. **راجع §8 بعد العكس**: هل زراعة بيانات مصطنعة وإثبات تجاهلها هي الصيغة التي قصدتها، أم تريد ضبطاً إضافياً؟

6. **لا تعتبر أي نتيجة هنا تحققاً من الحالة الحية** لقاعدة البيانات أو النشر.

**ما أوافقك عليه بلا تحفظ:** لا يلزم مسار طوارئ يتجاوز المصادقة. التعافي يكون بإصلاح التهيئة أو الجزء المعيب مع إبقاء المنع قائماً.
