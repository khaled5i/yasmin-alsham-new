## 2. العطل — الآلية الدقيقة

### 2.1 الحالة قبل الإصلاح

```js
const useRealtime = !(window as any).Capacitor && annotationId !== '__design_summary__'
if (useRealtime) {
  try {
    const tokenRes = await fetch('/api/soniox-token')
    if (tokenRes.ok) {
      /* ... إنشاء WebSocket وتسجيل onopen/onmessage/onerror/onclose ... */
    }
    // ← لا يوجد else. لا شيء يحدث إطلاقاً.
  } catch (e) {
    soxFinishedRef.current = true   // يعمل فقط عند رمي استثناء
  }
} else {
  soxFinishedRef.current = true     // يعمل فقط عند useRealtime === false
}
```

**نقطة المفتاح:** وفق معيار Fetch، لا يُرفض الوعد لمجرد حالة HTTP — الرفض يقع على فشل الشبكة فقط. لذلك رد `401` أو `403` أو `500`:

- لا يدخل `catch` → العلم لا يُضبط.
- لا يدخل `else` الخارجي → لأن `useRealtime === true`.
- لا يُنشأ `WebSocket` → `sonioxWsRef.current` يبقى `null`.
- `soxFinishedRef.current` يبقى `false` (ضُبط `false` في بداية `startRecording`).

### 2.2 كيف يتحوّل ذلك إلى ضياع التسجيل

**أ — `stopRecording`:** الشرط الأول يتطلب WS مفتوحاً، والثاني يتطلب `sonioxWsRef.current` غير فارغ. كلاهما يفشل، ولا `else` ثالث. **العلم يبقى `false`.**

**ب — `mediaRecorder.onstop`:** يبني الـblob ويضعه في `soxCurrentBlobRef` — **الصوت التُقط فعلاً وسليم** — ثم يستدعي `tryFinalizeAnnotation()`.

**ج — `tryFinalizeAnnotation`:** `if (!soxFinishedRef.current) return` ← يخرج هنا.

### 2.3 الأثر الفعلي

| البند | النتيجة |
|---|---|
| نص التفريغ | لا يوجد |
| **الملف الصوتي نفسه** | **يضيع — لا يُحفظ في التعليق إطلاقاً** |
| المسار الاحتياطي async | **لا يُستدعى** (داخل `tryFinalizeAnnotation` بعد نقطة الخروج) |
| رسالة خطأ للمستخدم | **لا توجد** |

الصوت **كان ملتقطاً وسليماً** ثم أُهمل بسبب علم لم يُضبط. المستخدم يظن أنه سجّل ملاحظة وهي غير موجودة.

### 2.4 هل العطل قائم اليوم؟

نعم، لكنه نادر: عند عدم ضبط `SONIOX_API_KEY` أو كونه القيمة النائبة (`soniox-token/route.ts:5-10` يعيد **500** صراحةً)، أو خطأ 5xx، أو وسيط شبكي يعيد صفحة خطأ. بعد المرحلة 4 يصبح `401` مساراً **روتينياً**.

## 4. التعديل 3 — تصحيح ادعاء خاطئ، لا تجميل

### 4.1 ما ادّعيتُه خطأً

قلتُ في النسخة 1 إن فشل التفويض «نتيجته النهائية التفريغ نفسه بتأخير بضع ثوانٍ». المراجع اعترض، والفحص أثبت أنه محقّ — **والمشكلة أوسع مما ذكر**.

مسار الملاحظات الاحتياطي ومسار ملخص التصميم **ليسا متكافئين**. الثاني عُولج والأول لم يُعالَج:

| | مسار الملاحظات (كان) | مسار ملخص التصميم |
|---|---|---|
| تحويل WAV | ❌ يرسل webm خاماً | ✅ `recordingBlobToWav` |
| شرطة مائلة ختامية | ❌ `...transcribe` | ✅ `...transcribe/` |
| إظهار الفشل للمستخدم | ❌ console فقط | ❌ console فقط |

**والدليل من تعليقات الكود نفسه** في مسار ملخص التصميم:

> `// لأن webm الخام من MediaRecorder يجعل معالج Soniox يتوقّف (timed out)`
> `// trailing slash لتجنّب توجيه 308 (trailingSlash:true) الذي يرفع الصوت مرتين`

و`trailingSlash: true` مؤكَّد في `next.config.ts`.

**الخلاصة:** مسار الملاحظات الاحتياطي كان يرفع الصوت **مرتين** بسبب 308، ثم يُرجَّح أن يفشل التفريغ بـtimeout لأنه webm خام. فالتعديلان 1 و2 كانا ينقذان الصوت ويوجّهانه إلى مسار معطوب.

### 5.2 ما تغيّر سلوكياً

| الحالة | قبل | بعد |
|---|---|---|

### 5.3 استدعاء مزدوج لـ `tryFinalizeAnnotation`؟

لا. الفرعان الجديدان يضبطان علماً فقط ولا يستدعيانها. وهي محميّة أصلاً: تُصفّر `soxCurrentBlobRef.current = null` ثم تخرج عند `if (!blob) return`.

### 5.4 مسائل التوقيت

`soxFinishedRef.current = true` في `startRecording` تُنفَّذ قبل إنشاء `MediaRecorder` بوقت طويل. والفرع الجديد في `stopRecording` متزامن ويسبق `onstop` الذي تُجدوِله `mediaRecorder.stop()`.

### 5.5 استهلاك الخدمات المدفوعة

تسجيلات كانت تضيع صامتة ستذهب الآن إلى `/api/soniox-async-transcribe`. يقابله خفض الرفع المزدوج إلى مفرد في كل استخدامات المسار. **الضبط النهائي في المرحلة 5** (تحديد معدّل + تحقق هوية).

## 7. التراجع — **أُعيدت كتابة هذا القسم بالكامل**

### 7.1 تصحيح خطأ في النسخة 1

النسخة 1 قالت: «إن وجب التراجع عن أحدهما، تراجع عن المرحلة 4 أولاً أو معها.»

**هذا خطأ، والمراجع محقّ في رفضه.** التراجع عن المرحلة 4 يعني إعادة `/api/soniox-token` إلى تسليم المفتاح الخام لأي طالب — أي **إعادة كشف سرّ لإصلاح عطل وظيفي**. وبعد تدوير المفتاح يصبح الأسوأ: غير آمن **و** معطّل معاً.

**القاعدة الصحيحة: حماية الأسرار لا يُتراجع عنها لإصلاح عطل وظيفي.**

### 7.2 التراجع عن هذه المرحلة وحدها

```bash
git diff src/components/InteractiveImageAnnotation.tsx     # راجع أولاً
git revert <hash>                                          # بعد الإيداع — المفضّل
```

**تحذير (من المراجع، وهو محقّ):** `git checkout -- <file>` يمحو **كل** التعديلات غير المودعة في الملف، لا تعديلات هذه المرحلة وحدها. لا تستخدمه إلا بعد `git diff` والتأكد أن لا شيء آخر في الملف. الأأمن هو الإيداع ثم `git revert`.

التغيير معزول: ملف واحد، لا ترحيلات، لا تغيير في العقود أو الأنواع أو المخطط، لا حالة مستمرة. لكن «معزول» **لا تعني «آمن تلقائياً»** — التحقق قبل التراجع لازم كالتحقق قبل التطبيق.

### 7.3 إن ظهر عطل صوتي بعد المرحلة 4

بالترتيب، **وحماية المفتاح باقية في كل الخيارات**:

1. **تراجع عن هذه المرحلة وحدها** إن ثبت أنها السبب — لا يمسّ حماية المفتاح.
2. **عطّل التفريغ اللحظي مؤقتاً**: اجعل `useRealtime = false` فيسلك الجميع المسار الاحتياطي الخادمي. الصوت يُحفظ، التفريغ متأخر، **والمفتاح لا يغادر الخادم**.
3. **أصلح إلى الأمام.**

**ممنوع:** إعادة نشر مسار يسلّم المفتاح للمتصفح.

## 8. نطاق المرحلة 4 — توسيع بناءً على ملاحظة المراجع

المراجع أشار إلى أن `/api/soniox-async-transcribe` **لا يتضمن تحقق هوية داخل معالجه**. تحققتُ: **صحيح** — المعالج يقرأ `SONIOX_API_KEY` ويستقبل `formData` مباشرة بلا أي فحص جلسة.

الأثر: حماية `/api/soniox-token` وحده **لا تحمي الخدمة المدفوعة**. المسار الثاني لا يسرّب المفتاح لكنه يتيح لأي شخص رفع صوت وتفريغه على حساب المالك. والتعديل 3 يزيد الاعتماد عليه.

**لذلك: المرحلة 4 يجب أن تغطي المسارين معاً، لا `soniox-token` وحده.** حُدِّث أدناه.

هذه **ملاحظة على الحالة القائمة سابقاً للتعديل** — لم أستدعِ الخدمة الحية ولم أجلب المفتاح.

## 9. ما أطلب من المراجع في الجولة القادمة

1. **تحقّق من التعديل 3 تحديداً** — هل نقلي لمعالجة ملخص التصميم أمين؟ خاصة `try/catch` الداخلي لتحويل WAV، وتغيّر شكل قراءة رد الخادم.
2. **ابحث عن مسار رابع** يصل إلى `mediaRecorder.onstop` مع `soxFinishedRef === false` ولم أغطِّه.
3. **راجع §7.3**: هل خيار `useRealtime = false` يُبقي حماية المفتاح فعلاً في كل الحالات؟
4. **قيّم قرار §4.3**: هل تأجيل رسالة الفشل المرئية للمستخدم مقبول، أم يجب أن يسبق الاعتماد؟
5. **لا تعتبر أي نتيجة هنا تحققاً من الحالة الحية** لقاعدة البيانات أو النشر.
