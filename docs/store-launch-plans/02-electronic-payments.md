# الخطة الثانية — الدفع الإلكتروني ودورة طلب الأقمشة

## تكليف المساعد المنفذ

أنشئ رحلة بيع آمنة لمتجر أقمشة ياسمين الشام من مراجعة السلة إلى الطلب والدفع والشحن والاسترداد والمطابقة المالية. هذه خطة مستقلة أُعدت في 19 سبتمبر 2026؛ لا تنفذ إنتاجيًا حتى يصدر تكليف تنفيذ. لا تُنشئ فاتورة أو دفعة حقيقية للاختبار، ولا تعدل تاريخ المحاسبة أو طلبات التفصيل.

## سياق ومستندات البدء

المشروع Next.js App Router/Supabase. صفحات الأقمشة `/fabrics` و`/fabrics/[id]`؛ التسعير في `src/lib/fabric-display-pricing.ts` و`src/store/fabricStore.ts`. توجد روابط `inventory_item_id` و`inventory_color_id`. راجع `src/lib/services/fabric-inventory-service.ts` و`supabase/migrations/20260823161026_sync_fabric_sales_with_inventory.sql` و`20260823162112_preserve_historical_fabric_sales_inventory.sql`، ومسار `src/app/api/alostaz/send-fabric-invoice/route.ts` وترحيلات حماية الفواتير المرسلة. البيع المحاسبي الحالي ينشئ حركات مخزون؛ إضافة خصم جديد فوقه قد تخصم مرتين.

لا يوجد في الفحص الحالي checkout للأقمشة. افترض أن الخطة الأولى ستوفر عناصر بمراجع صنف/لون/كمية/وحدة بيع؛ إن لم توجد، ابدأ بواجهة بيانات تجريبية دون بناء سلة منافسة. توجد ثغرات أولية في المستخدمين والخدمات والملفات؛ اجعل إغلاقها شرط إطلاق.

## المرحلة 0: اعتماد الاختيارات

اجمع من المالك: الكيان والسجل والحساب البنكي وشهادة الضريبة إن وجدت؛ سياسة البيع بالمتر والقطعة والحد الأدنى؛ شمول الأسعار للضريبة؛ الشحن والاستلام؛ وقت القص؛ من يملك الاسترداد؛ نظام إصدار الفاتورة المعتمد.

ابدأ بمقارنة عرض ميسر مع PayTabs وخيار البنك الحالي، واختر مزودًا واحدًا للإصدار الأول. ميسر يدعم تكامل API وبيئة اختبار، ويطلب مستند نشاط وحسابًا تجاريًا مرتبطًا به ومراجعة المنتجات والسياسات والتواصل. الترشيح للتقييم مناسب للبنية الحالية، وليس حكمًا بأنه الأرخص أو ضمان قبول. [متطلبات ميسر](https://moyasar.com/ar/resources/faqs/).

الوسائل المستهدفة: مدى وVisa وMastercard وApple Pay، بشرط تفعيل كل وسيلة في العقد. أكد مع المزود رسوم العملية والثابتة والضريبة ورسوم الاسترداد والاعتراض والتسوية والاحتياطي والحدود، وتفعيل البطاقات الدولية. لا تفترض أن حساب البنك أو جهاز الشبكة الحالي يفعّل التجارة الإلكترونية تلقائيًا.

ابدأ بصفحة دفع مستضافة، أو مكونات رسمية ترسل بيانات البطاقة للمزود مباشرة. لا يصل PAN أو CVV إلى خادم الموقع أو سجلاته أو Supabase. نطاق PCI وSAQ يحدد وفق طريقة الربط ومعايير الأهلية والبنك؛ الاستضافة الخارجية لا تعني إعفاء الموقع من المسؤوليات الأمنية. [مرجع PCI SSC](https://www.pcisecuritystandards.org/faqs/1588/).

## المرحلة 1: نموذج طلبات مستقل عن التفصيل

أسماء مقترحة، تُعتمد بعد جرد قاعدة البيانات:

| الجدول | الغرض والقيود |
|---|---|
| `fabric_store_orders` | معرف داخلي ورقم عرض، مالك أو جلسة زائر آمنة، العملة SAR، المجاميع، حالة الطلب، نسخ السياسات المعتمدة، timestamps |
| `fabric_store_order_items` | snapshot الاسم والكود واللون ووحدة البيع وطول القطعة والكمية والسعر والخصم والضريبة؛ مراجع المخزون؛ التاريخ لا يتغير بتغير الكتالوج |
| `fabric_store_order_addresses` | الحد الأدنى من بيانات المستلم والعنوان، وصول خاص ومدة احتفاظ محددة |
| `fabric_store_payment_attempts` | طلب واحد ومحاولات متعددة، مزود ومعرف دفع فريد ومبلغ وعملة وبيئة وحالة ومفتاح idempotency |
| `fabric_store_payment_events` | سجل أحداث فريد حسب المزود والبيئة ومعرف الحدث؛ payload منقح، حالة المعالجة وأسباب الفشل |
| `fabric_store_stock_reservations` | SKU وكمية ومدة انتهاء وحالة ومصدر؛ قيد يمنع تكرار الحجز للعملية نفسها |
| `fabric_store_refunds` | الاستردادات الجزئية والكاملة وحالتها ومراجعها ومبلغها؛ لا تتجاوز المتحصل بعد الاستردادات السابقة |
| `fabric_store_outbox` | مهام موثوقة للمحاسبة والإشعارات والشحن مع retry؛ مفتاح فريد يمنع تكرار الأثر |

الأموال بوحدات هللة صحيحة، والكميات NUMERIC بدقة ثابتة أو وحدات طول صحيحة متفق عليها. لا تستخدم float للمجاميع. عرّف التقريب للسطور والضريبة والإجمالي قبل التنفيذ. الخادم يعيد الحساب من بيانات موثوقة؛ لا يقبل مبلغ المتصفح أو عنوان شحن كائنًا مفتوحًا غير متحقق.

افصل حالات الدفع (`pending/authorized/paid/failed/refunded/partially_refunded`) عن التنفيذ (`unfulfilled/preparing/shipped/delivered/cancelled`). authorization ليس تحصيلًا. لا تسمح لموظف شحن بتحويل طلب إلى paid. عرّف الانتقالات الممكنة ومصدر كل انتقال في جدول اختبارات.

## المرحلة 2: checkout وعقد API

1. `/api/fabric-store/quote`: التحقق من الصنف واللون والوحدة والكمية والسعر والخصم والشحن والضريبة على الخادم، وإرجاع عرض محدود الصلاحية. لا يتحول المخزون 3.5 متر إلى سعر متر أو العكس بصمت.
2. `/fabrics/checkout`: بيانات المستلم وهاتف صحيح وعنوان ووسيلة توصيل وتكلفة ومدة متوقعة وملخص إجمالي ظاهر. عرض سياسة قص الأقمشة والاسترداد والموافقة على الشروط؛ التسويق اختياري منفصل.
3. `/api/fabric-store/checkout`: إنشاء snapshot طلب وحجز ذري صالح وإنشاء محاولة دفع بمفتاح إعادة محاولة. اربط مفتاح الطلب بصاحب الجلسة وبصمة المدخلات؛ إعادة استخدامه ببيانات مختلفة تُرفض.
4. ابدأ رحلة المزود من الخادم بالمبلغ والعملة ومعرف الطلب وعناوين العودة المسموحة. خزّن معرف المحاولة قبل عرض رابط التحويل متى سمحت آلية المزود.
5. صفحة `/fabrics/payment/return`: تعرض «جارٍ التحقق» ثم تستعلم عن الحالة الموثقة من خادمنا؛ `status=paid` في الرابط ليس إثباتًا.
6. صفحة تأكيد وتتبّع تعرض أقل بيانات لازمة. للزائر استخدم جلسة cookie آمنة أو رابطًا عشوائيًا عالي العشوائية محدود الصلاحية محفوظ hash، مع حماية من التخمين. رقم الطلب/الهاتف وحده لا يخول قراءة العنوان أو الفاتورة.

الشراء كضيف هو الاختيار المبدئي لتقليل التعقيد؛ الحساب اختياري بعد تأمين نموذج العملاء. احمِ طلبات الجلسة من CSRF حسب طريقة الاعتماد، وطبّق حدود معدل وكمية وحجم مدخلات، ولا تقبل روابط redirect عشوائية.

## المرحلة 3: المخزون والتزامن — شرط إطلاق

- السلة لا تحجز؛ checkout يحجز ذريًا مع أقفال صفوف وقاعدة: الكمية المتاحة = الفعلية ناقص الحجوزات الصالحة.
- كل قناة تبيع نفس المخزون، بما فيها شاشة دخل المحل، يجب أن تحترم الحجوزات. حجز الموقع وحده لا يمنع موظف المحل من بيع القطعة نفسها. إن تعذر توحيد القنوات، خصص مخزونًا منفصلًا للموقع قبل إطلاق البيع بدل الادعاء بأن المشكلة حلت.
- اختبر القماش الذي يباع كاملًا ولا تسمح بشراء جزء أو إنشاء حجزين متعارضين له.
- أنشئ adapter محاسبيًا واحدًا: عند اعتماد البيع، أنشئ سجل الدخل والحركة عبر مسار واحد فقط، مع تحويل/استهلاك الحجز في المعاملة نفسها المناسبة. لا تنفذ تحديث كمية يدويًا إضافة إلى trigger الدخل.
- الحجز له TTL ومهمة تنظيف قابلة للتكرار. لا تُنهِ حجزًا بينما دفعة حالتها مجهولة دون سياسة تسوية؛ راجع المزود ثم حرره أو علّق الحالة.
- دفعة ناجحة تصل بعد انتهاء الحجز: تحقق ذريًا من إمكانية تخصيص المخزون؛ إن تعذر، حالة مراجعة واسترداد منضبط وإشعار، دون مخزون سالب أو وعد بالتسليم.
- استرداد المال لا يعيد القماش المقصوص إلى المخزون آليًا. إعادة المخزون تحتاج استلامًا وفحصًا وتحديد طول صالح وإجراء حركة مستقلًا موثقًا.

## المرحلة 4: Webhook ومصدر الحقيقة

في `/api/payments/<provider>/webhook` تحقق من آلية التوثيق الرسمية للمزود ولا تخترع اسم header أو توقيعًا. مثال ميسر: الوثيقة الحالية تصف `secret_token` و`live` ومعرف حدث وتكرار التسليم؛ لا تفترض أنها HMAC. أعد جلب الدفع من API الخادمي للتحقق من الحساب والبيئة والمبلغ والعملة ومعرف الطلب والحالة. [توثيق ميسر للأحداث](https://docs.moyasar.com/api/other/webhooks/webhook-reference).

احفظ الحدث أولًا في سجل موثوق ثم رد بسرعة، وأكمل المعالجة عبر outbox/worker دائم. لا تستخدم مهمة fire-and-forget قد تنقطع بعد انتهاء Serverless. لا ترسل 2xx قبل تأمين حفظ الحدث؛ وفي الحدث المكرر أعد النجاح دون أثر إضافي.

قفل الطلب وفهارس uniqueness يضمنان أن دفعًا ناجحًا يُعتمد مرة واحدة فقط. الأحداث المتأخرة أو غير المرتبة لا تُرجع paid إلى failed؛ راجع الحالة الحالية لدى المزود. امنع اعتماد محاولة تخص طلبًا آخر. إذا نجحت محاولتان لطلب واحد، سجّل الزيادة وحالة مراجعة/استرداد؛ لا تنشئ شحنتين.

## المرحلة 5: إدارة الطلب والتشغيل

- قائمة مستقلة لطلبات متجر الأقمشة بفلاتر الدفع والتجهيز والشحن والاسترداد، مع صلاحيات محددة وسجل تدقيق.
- تأكيد طلب تلقائي ورقم مرجعي وتفاصيل الأصناف والكمية والإجمالي. استخدم قنوات الإشعارات المعتمدة مع منع تكرار الإرسال.
- شحن: منطقة وتكلفة ومدة، عنوان وطني/مختصر وفق شركة الشحن، بوليصة ورقم تتبع وتحديثات، أو استلام فرع بإثبات تسليم. يمكن بدء البوليصة يدويًا بإجراء موثق، دون اختراع تكامل ناقل.
- استرداد كامل وجزئي عبر عملية خادمية مخولة، بمفتاح عدم تكرار وأثر تدقيق. سجّل pending إلى أن يؤكده المزود، وميّز رد المبلغ عن إلغاء الطلب ورد المخزون.
- المحاسبة: لا يُعد إرسال الأموال إلى الحساب البنكي مساويًا لقيمة المبيعات. سجّل الإجمالي والرسوم والضريبة على الرسوم وصافي التسوية والاستردادات منفصلة وفق اعتماد المحاسب.
- لا تستخدم مسارات فواتير التفصيل للمتجر. حقق عقد الأستاذ للفرع والمنتجات والضريبة وتوقيت الاعتراف، وأنشئ معرف ارتباط فريد يمنع إرسال الفاتورة مرتين. فشل الأستاذ بعد نجاح الدفع يصبح مهمة إعادة إرسال، ولا يكرر التحصيل.
- الفاتورة الضريبية ليست إيصال بوابة الدفع. تحقق من امتثال نظام الإصدار وإشعارات الدائن عند انطباق ضريبة القيمة المضافة ومراحل الربط. [مراحل الفوترة — هيئة الزكاة والضريبة والجمارك](https://zatca.gov.sa/ar/E-Invoicing/Introduction/Pages/Roll-out-phases.aspx).
- مهمة مطابقة دورية تقارن المبالغ والمحاولات مع المزود، وتكشف الدفع بلا طلب مؤكد أو طلب paid بلا دليل أو تسوية ناقصة، مع تنبيهات قابلة للتصرف.

## اختبارات قبول إلزامية في Sandbox

| السيناريو | النتيجة المطلوبة |
|---|---|
| نجاح/فشل/إلغاء/تعثر 3DS | حالة صحيحة دون اعتماد المتصفح؛ إمكانية إعادة المحاولة |
| إغلاق الصفحة بعد الدفع | الطلب يُعتمد عبر webhook/المطابقة، دون احتياج رجوع العميل |
| ضغط دفع مرتين أو timeout بعد إنشاء الدفع | محاولة آمنة قابلة للاسترجاع دون خصم مكرر |
| webhook مكرر أو متأخر أو ترتيبه مختلف | طلب واحد وحركة واحدة وفاتورة واحدة |
| webhook مزور/مبلغ أو عملة أو بيئة مختلفة | رفض أو حجر للمراجعة دون اعتماد |
| متسوقان وآخر قطعة، أو بيع محل متزامن | لا تجاوز مخزون ولا بيع الحجز مرتين |
| تغيير السعر بعد إضافته للسلة | إعادة عرض واعتماد السعر الجديد قبل الدفع |
| انتهاء الحجز ثم نجاح الدفع | تخصيص آمن أو معالجة استرداد؛ لا حالة صامتة |
| انقطاع قاعدة البيانات/المحاسبة/الإشعارات | retry موثوق دون فقد حدث أو مضاعفة أثر |
| استرداد جزئي ثم كامل أو طلب مكرر | إجمالي مردود لا يتجاوز المتحصل ولا تكرار |
| مستخدم يطلب طلب غيره | منع الوصول وعدم كشف العنوان أو معلومات الدفع |
| جوال وRTL/LTR وعودة من Apple Pay | ملخص واضح وحالة صحيحة دون كسر التنقل |

## إطلاق وتراجع وتسليم

افصل مفاتيح test/live وURLs والأسرار. إذا استُخدم Apple Pay، نفذ إثبات النطاق/متطلبات المزود للطريقة المختارة واختبر على جهاز مدعوم. لا تضع secret key في NEXT_PUBLIC. الاستضافة تحتاج backend فعليًا؛ `CAPACITOR_BUILD=true` ينتج static export ولا يقوم مقام خادم الدفع.

سلّم ERD، ترحيلات وإجراءات تراجع غير هدامة، مخطط الحالات، توثيق endpoints والـjobs، إعدادات بلا قيم أسرار، نتائج Sandbox، ودليل تشغيل للمحاسب وخدمة العملاء. الإطلاق يتطلب قبول المزود وإغلاق الثغرات الحرجة وتطابق الفاتورة والشحن وموافقة المالك ضمن مهمة الإطلاق. عند العطل أوقف إنشاء دفعات جديدة مع استمرار استقبال أحداث المدفوعات القائمة والمطابقة والاسترداد؛ لا توقف webhook كطريقة تراجع.
